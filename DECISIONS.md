# DECISIONS — append-only ADR (Assignment 6)

## D-001 Lab 5 is the base and is never modified; Task 6 lives in its own tree and remote dirs
Context: Lab 5 is not graded yet; its public URL (10.1.75.53:3269), direct backend ports
(3270, 3271) and repo must keep working. Task 6 says "extend your previous application".
Decision: copy Lab 5's app/lb/loadgen/scripts into this folder and extend them (v2/v3).
On the lab boxes everything deploys into `~/assignment6`; `~/assignment5` stays intact.
`scripts/rollback_lab5.sh` restores the Lab 5 processes in under a minute.
Consequence: the public URL is served by LB v2 (a strict superset of v1: all four Lab 5
algorithms remain selectable), so Lab 5's demo still works through the same URL.
Date: 2026-09-04

## D-002 sys4 backend binds port 3001 — port 3000 there is the Contour project
Context: `ss -ltnp` on sys4 shows nginx on :3000 (Contour pond-planning frontend, public
3272), plus Postgres 15432 and Redis 16379. Lab 5's sys4 backend was stopped on Sep 1
(RESTORE-CHAT.txt on sys4 documents this).
Decision: Task 6 backend on sys4 listens on 3001. Only the LB needs public exposure; the
LB reaches backends over the Docker bridge (172.17.0.73:3001). Nothing on sys4 other than
`~/assignment6` is touched.
Date: 2026-09-04

## D-003 Database = SQLite (WAL) via node:sqlite in a dedicated DB service on sys1:5270
Context: no Redis/Postgres installable without root on sys1; Lab 5 used an append-only
JSONL store with no uniqueness guarantee. Task 6 requires unique message ids and
duplicate rejection by the database. Node 18 on sys1 lacks node:sqlite (needs ≥ 22.13).
Decision: install a user-local static Node 22 into `~/node` on sys1 (same method Lab 5
used for sys2-4). `app/db_service.js` owns the single SQLite file: `messages.id` is the
PRIMARY KEY, `UNIQUE(room, seq)` for ordering, `INSERT ... ON CONFLICT(id) DO NOTHING`
inside a transaction is the duplicate guard; duplicates are counted and audited.
The HTTP/WS surface stays compatible with Lab 5's state service so backends change little.
Port 5270 (not 5269) so Lab 5's state service keeps running untouched.
Consequence: one shared source of truth (documented single point of failure, same as
Lab 5 D-006); Lab 5 data (users, rooms, 111k messages) is migrated in at first boot.
Date: 2026-09-04

## D-004 Message ids are generated by the CLIENT (UUID v4) and are the idempotency key
Context: retries and reconnections happen client-side; only the client knows two sends
are "the same message". Server-generated ids cannot detect a client retry.
Decision: the browser/loadgen mints `id` when the message is composed and reuses it on
every retry. Backends accept `id` in the body or an `Idempotency-Key` header; a missing id
is minted server-side (still unique, but then a retry is a new message by definition).
Three layers of defence: per-backend LRU of recent ids (fast path), the DB PRIMARY KEY
(authoritative, across all backends), and the UI hiding a duplicate `seq` it already has.
A duplicate send returns HTTP 200 `{ok:true, duplicate:true, seq, id}` — idempotent success,
never an error the client would retry again.
Date: 2026-09-04

## D-005 Dynamic selection = "adaptive" score; slow backends are DEGRADED, not ejected
Context: the task requires selection by response time and/or system load, and Lab 5's
D-011 showed that ejecting a slow-but-alive 1-core backend causes churn.
Decision: score(b) = EWMA_rt(b) × (1 + in_flight(b)) × (1 + cpu_load(b)); pick the minimum
(peak-EWMA / least-loaded family). EWMA is fed by every proxied request AND by the health
probe's own latency, so idle backends keep a fresh estimate. cpu_load comes from the
backend's /health JSON (process CPU% and 1-min loadavg, normalised to its 1 core).
New backends start with score 0 (optimistic) so they receive traffic immediately; 5 %
exploration keeps every UP backend sampled. Health states: UP, DEGRADED (probe slow or
load high → still routable, score penalised), DOWN (connect refused / timeouts ≥
fail_threshold), DRAINING (asked to leave: finish in-flight, take nothing new).
Fail-open from Lab 5 is kept: the last routable backend is never ejected.
Date: 2026-09-04

## D-006 Membership: push registration + pull discovery + config reload, all three
Context: "initialize additional backend systems while the application is running; the LB
should automatically detect the new backend".
Decision: (1) backends POST /lb/register {id, host, port, weight} with a shared token at
boot and every 10 s as a heartbeat; (2) the LB probes `discovery.candidates` (known
host:port slots such as sys3:3000, sys4:3001) every few seconds and admits any that answer
/health, so even a backend that cannot reach the LB's API is found; (3) lb.conf.json is
re-read when its mtime changes. Dynamically-added backends that stay DOWN for
`prune_after_s` are dropped from the pool; statically configured ones are kept as DOWN.
Date: 2026-09-04
